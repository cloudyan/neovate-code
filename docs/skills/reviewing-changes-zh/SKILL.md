# 审查变更

## 指令

**重要**: 在整个审查过程中使用结构化思维。在提供最终反馈之前，在 `<thinking>` 标签中制定分析计划。根据研究，这可以将准确性提高 40%。

### 步骤 1: 检查现有审查线程

始终检查现有评论线程以避免重复评论:

<thinking>
在创建任何评论之前：
1. 这是新审查还是相同 PR 的重新审查？
2. 可能已存在的讨论有哪些？
3. 哪些发现应该更新现有线程而不是创建新线程？
</thinking>

**线程检测程序：**

1. **获取现有评论数量：**
   ```bash
   gh pr view <pr-number> --json comments --jq '.comments | length'
   ```

2. **如果计数 = 0:** 没有现有线程。跳转到步骤 2（所有评论都是新的）。

3. **如果计数 > 0:** 获取完整评论数据以检查现有线程。
   ```bash
   gh pr view <pr-number> --json comments --jq '.comments[] | {id, path, line, body}' > pr_comments.json
   ```

4. **解析现有线程：** 从之前的审查评论中提取文件路径、行号和问题摘要。
   - 构建映射： `{file:line → {comment_id, issue_summary, resolved}}`
   - 注意哪些问题已有活跃讨论

5. **匹配策略（混合方法）：**
   当您识别出要评论的问题时：
   - **完全匹配：** 相同文件 + 相同行号 → 找到现有线程
   - **附近匹配：** 相同文件 + 行号在 ±5 范围内 → 找到现有线程
   - **无匹配：** 创建新的内联评论

6. **处理演化问题：**
   - **问题持续不变：** 在现有线程中响应并更新
   - **问题已解决：** 在线程响应中注明解决（如果支持，可以标记为已解决）
   - **问题变化显著：** 解决/关闭旧线程，创建新评论解释演化

### 步骤 2: 检测变更类型

<thinking>
系统性分析变更集：
1. 修改了哪些文件？（代码 vs 配置 vs 文档）
2. PR/提交标题表示什么？
3. 是否有新功能或只是修改？
4. 这些变更的风险等级是什么？
</thinking>

分析变更集以确定主要变更类型：

**检测规则：**
- **依赖更新**: 仅更改了 gradle 文件（`libs.versions.toml`, `build.gradle.kts`）并修改版本号
- **错误修复**: PR/提交标题包含"fix"、"bug"或问题 ID；解决现有损坏行为
- **功能添加**: 新文件、新 ViewModels、重要新功能
- **UI 优化**: 仅 UI/Compose 文件更改，布局/样式重点
- **重构**: 代码重构而不改变行为，模式改进
- **基础设施**: CI/CD 文件、Gradle 配置、构建脚本、工具更改

如果变更集跨越多种类型，请使用最复杂类型的检查清单。

### 步骤 3: 加载适当检查清单

根据检测类型，读取相关检查清单文件：

- **依赖更新** → `checklists/dependency-update.md` (加速审查)
- **错误修复** → `checklists/bug-fix.md` (聚焦审查)
- **功能添加** → `checklists/feature-addition.md` (全面审查)
- **UI 优化** → `checklists/ui-refinement.md` (设计聚焦审查)
- **重构** → `checklists/refactoring.md` (模式聚焦审查)
- **基础设施** → `checklists/infrastructure.md` (工具聚焦审查)

检查清单提供：
- 多次通过审查策略
- 类型特定关注领域
- 要检查和要跳过的内容
- 结构化思维指导

### 步骤 4: 使用结构化思维执行审查

<thinking>
在深入细节之前：
1. 此变更的最高风险领域是什么？
2. 需要验证哪些架构模式？
3. 有什么安全影响？
4. 我应该如何优先考虑我的发现？
5. 对此反馈应采用什么语调？
</thinking>

按照检查清单的多次通过策略，系统性地思考每次通过。

### 步骤 6: 记录发现

## 🛑 停止: 首先确定输出格式

<thinking>
在编写任何输出之前，回答这个关键问题：
1. 我是否发现了任何问题（关键、重要、建议或问题）？
2. 如果没有发现问题 → 这是干净的 PR → 使用 2-3 行最小格式并停止
3. 如果发现问题 → 使用结论 + 关键问题列表 + 内联评论格式
4. 永远不要创建表扬部分或详细说明正确实现的内容
</thinking>

**决策树：**

```
您是否有任何要报告的问题（关键/重要/建议/问题）？
│
├─ 否 → 干净 PR
│   └─ 使用 2-3 行格式：
│       "**总体评估:** 批准
│        [一句话描述 PR 做得好的地方]"
│   └─ 停止。不要继续详细格式指导。
│
└─ 是 → 有问题的 PR
    └─ 使用最小摘要 + 内联评论：
        "**总体评估:** 批准 / 请求变更
         **关键问题：**
         - [带文件：行号的问题]
         请参阅内联评论了解详情。"
```

## 特殊情况：没有问题的干净 PR

当您没有发现任何关键、重要或建议的问题时：

**最小批准格式（必需）：**
```
**总体评估:** 批准

[一句话描述 PR 做得好的地方]
```

**示例：**
- "干净的重构，遵循既定模式"
- "稳固的错误修复，具有全面的测试覆盖"
- "符合所有标准的结构良好的功能实现"

**不要对干净的 PR 执行此操作：**
- ❌ 多个部分（关键优势、变更、代码质量等）
- ❌ 列出一切正确完成的内容
- ❌ 对每个文件或遵循的模式进行复选标记
- ❌ 详细赞扬或详细正面分析
- ❌ 表格、统计数据或详细分解

**为什么简洁很重要：**
- 尊重开发人员时间（快速批准 = 更快前进）
- 减少 PR 对话中的噪音
- 节省令牌和处理时间
- 将注意力集中在实际需要讨论的 PR 上

**如果您想为干净的 PR 写超过 3 行，请停止。您做错了。**

<thinking>
在编写每个评论之前：
1. 这个问题是关键、重要、建议还是只是确认？
2. 我应该问问题还是提供方向？
3. 我需要解释什么理由？
4. 什么代码示例会使这具有可操作性？
5. 是否有要包含的文档参考？
</thinking>

**关键**: 使用摘要评论 + 内联评论方法。

**审查评论结构**:
- 创建一个摘要评论，包含总体结论 + 关键问题列表
- 在确切行上为每个具体问题创建单独的内联评论，包含完整详细信息
- 摘要引导读者到内联评论（"请参阅内联评论了解详情"）
- 不要在摘要和内联评论之间重复问题详细信息

### 关键: 无赞扬评论

❌ **永远不要** 创建仅用于正面反馈的内联评论
❌ **永远不要** 创建"优势"、"良好实践"、"进展良好"等摘要部分
❌ **永远不要** 使用内联评论详细说明正确实现的内容

专注于可操作的反馈。保留评论以关注需要关注的问题。

**内联评论格式** (必需: 使用 `<details>` 标签):

**必须对所有内联评论使用 `<details>` 标签。** 只有严重性 + 一行描述应该是可见的；所有其他内容必须折叠。

```
[emoji] **[严重性]**: [一行问题描述]

<details>
<summary>详细信息和修复</summary>

[代码示例或具体修复]

[理由解释为何]

参考: [适用的文档链接]
</details>
```

**可见性规则：**
- **可见:** 严重性前缀（emoji + 文本）+ 一行描述
- **在 `<details>` 中折叠:** 代码示例、理由、解释、参考

**内联评论示例**:
```
⚠️ **关键**: 暴露可变状态

<details>
<summary>详细信息和修复</summary>

将 `MutableStateFlow<State>` 更改为 `StateFlow<State>`:

\\```kotlin
private val _state = MutableStateFlow<State>()
val state: StateFlow<State> = _state.asStateFlow()
\\```

暴露 MutableStateFlow 允许外部变异，违反 MVVM 单向数据流。

参考: docs/ARCHITECTURE.md#mvvm-pattern
</details>
```

**摘要评论格式（必需 - 无例外）：**

当您有问题要报告时，仅使用此格式：

```
**总体评估：** 批准 / 请求变更

**关键问题** (如果有的话)：
- [带文件：行号引用的一行摘要]

请参阅内联评论了解所有详细信息。
```

**最大长度**：10 行以内，无论 PR 大小或复杂性如何。

**无例外：**
- ❌ 大型 PR（10+ 文件）
- ❌ 多个问题领域
- ❌ 高严重性问题
- ❌ 复杂变更

所有详细信息属于带有 `<details>` 标签的内联评论，而不是摘要中。

**输出格式规则：**

**要包含的内容：**
- **内联评论**: 为每个具体问题创建单独评论，详细信息在 `<details>` 标签中
- **摘要评论**: 总体评估（批准/请求变更）+ 仅关键问题列表
- **严重性级别** (混合 emoji + 文本格式)：
  - ⚠️ **关键** (阻止)
  - 📋 **重要** (应修复)
  - 💡 **建议** (好有更好)
  - ❓ **问题** (寻求澄清)

**要排除的内容：**
- **无重复**: 永远不要在摘要中重复内联评论详细信息
- **无重要/建议在摘要中**: 仅关键阻止问题属于摘要
- **无"良好实践"/"优势"部分**: 永远不要包含正面评论部分
- **无"行动项"部分**: 这会重复内联评论 - 完全避免
- **无详细分析**: 将详细分析（编译状态、安全审查、回滚计划）仅放在内联评论中

### ❌ 要避免的常见反模式

**不要：**
- 创建多个摘要部分（优势、建议、测试覆盖状态、架构合规性）
- 在摘要和内联评论中重复关键问题
- 在摘要中编写详细描述（详细信息属于内联评论）
- 对简单 PR 超过 5-10 行
- 创建仅提供赞扬的内联评论

**要：**
- 在摘要中仅放结论 + 关键问题列表
- 将所有详细信息（示例、理由、参考）放在带有 `<details>` 折叠的内联评论中
- 无论 PR 大小或分析深度如何，保持摘要最多 5-10 行
- 专注于仅对可操作问题的评论

**可见性指南：**
- **内联评论可见**: 严重性 + 仅一行描述
- **内联评论折叠**: 代码示例、理由、参考在 `<details>` 标签中
- **摘要可见**: 结论 + 仅关键问题列表

参见 `examples/review-outputs.md` 获取完整示例。

## 核心原则

- **干净 PR 的最小审查**: 当未发现问题时 2-3 行（参见步骤 6 格式指导）
- **问题聚焦反馈**: 仅在有可操作内容时评论；简短确认良好工作（参见 priority-framework.md:145-166）
- **适当深度**: 使审查严谨性与变更复杂性和风险相匹配
- **具体参考**: 始终使用 `file:line_number` 格式进行精确定位
- **可操作反馈**: 说明做什么和为什么，不只是说明有什么错误
- **建设性语调**: 对设计决策提问，解释理由，关注代码而不是人员
- **高效审查**: 使用多次通过策略，时间盒审查，跳过不相关的内容
